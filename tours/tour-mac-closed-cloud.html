The Mac-Closed Cloud Lane

How a plain browser — with the user's desktop machine switched off — renders and drives cloud agent sessions directly against the agnt platform: auth, discovery, streaming, sending, and the gating that keeps the two data lanes from trampling each other.

Generated 2026-09-01 · synthesized from four parallel code explorations across deus-machine (branch zvadaadam/merge-agnt-codebase, uncommitted) and agnt (merged & deployed). Read top-to-bottom for the model; expand the ▸ details blocks when you need expert depth.

The 2-minute picture

Deus Machine is normally a three-process desktop app: a React frontend talks to a Node backend on your Mac over one WebSocket (the q: protocol), and that backend talks to agents — local ones via agent-server, cloud ones via the agnt platform. Every byte the UI renders flows through the Mac.

“Mac-closed” is the scenario where that Mac is off. You open app.deusmachine.ai on your phone or any browser, and the frontend — the same React app — talks to agnt directly: it authenticates, finds your cloud sessions, opens a WebSocket straight to the session's Durable Object, renders the live transcript, and sends new turns. No deus backend anywhere in the path. The same direct machinery also runs on the desktop behind a flag (deus.cloudDirect); collectively it's called Path B or the direct lane.

Two repos, five slices:

  • Auth & tokens — WorkOS login via the deus-cloud worker mints a 24-hour deus_cloud_session bearer; a per-session exchange converts it into short-lived, single-session session_tokens. (agnt: deployed)
  • Discovery — two dashboard REST endpoints list your orgs and their sessions; cloudDataAdapter.ts reshapes them into the sidebar's data model. (agnt: deployed; deus: uncommitted)
  • Render lane — cloudSessionSocket → cloudFrameHandler → agentEventFold → TanStack cache → React. A snapshot-first, seq-free stream.
  • Send lane — the composer routes through directSessionRegistry to a message.send frame on the same socket; agnt admits, echoes, queues, dispatches.
  • Lane gating — useIsDirectSession decides, per session, which lane owns the transcript; the q: client's interceptor seam keeps the Mac transport dark on the web.
The browser stops being a thin client to your Mac and becomes a first-class agnt client — same React app, different transport underneath.

Everything below is the same picture at increasing magnification. The five numbered sections give you the working mental model; the collapsible blocks inside them hold the expert detail.

Key concepts

deus_cloud_session bearer
A 24-hour HS256 JWT minted by the deus-cloud worker after WorkOS login. Claims: {iss:"deus-cloud", aud:"agnt-backend", sub:accountId, type:"deus_cloud_session", client}. It proves who you are to agnt's /dashboard/* surface (discovery, exchange, key minting). It can never open a session socket by itself.
session_token
A short-lived JWT (60 s–24 h, default 1 h) from POST /dashboard/sessions/:sessionId/token. Claims: {sub:accountId, aud:orgId, sid:sessionId, type:"session_token"}. Scoped to exactly one session — it can read the session snapshot and open its WebSocket, nothing else. All writes then travel as frames on that socket.
provider_session_id
agnt's session id, stored on the deus session row. Its presence (together with workspace_kind === "cloud") is the single fact that flips a session onto the direct lane. In pure web-direct mode the deus id and the provider id are the same string.
Direct lane (Path B) vs Mac lane
Two ways to fill the same UI. Mac lane: frontend ⇄ deus backend over q:; the backend owns history (SQLite) and relays agnt. Direct lane: frontend ⇄ agnt with no backend in the path; the DO's snapshot is the history. Path B runs Mac-closed on the web, or flag-gated (deus.cloudDirect) on a desktop that still has its backend.
The q: protocol
Deus's single-WebSocket query protocol to the Mac backend: q:subscribe / q:snapshot / q:delta for reactive reads, q:mutate for sync writes, q:command for async actions, q:event for ephemeral push. Defined in shared/events.ts; client in apps/web/src/platform/ws/query-protocol-client.ts.
The fold
agentEventFold.ts: feeds canonical agent events through the engine's reducer (reduceConversationWithChanges from @zvada/agent-server/protocol) and projects the resulting changes into the TanStack messages cache. It is the one writer module for ["sessions","messages", id] — both lanes go through it.
The echo
The user's own message, re-materialized as a transcript row with the derived id echo-${turnId}. Three independent producers (optimistic composer bubble, agnt's admission broadcast, the engine's own echo) all derive the same id, so they converge on one row with zero reconciliation code.
RepoGroup / Workspace-item mapping
The sidebar's data model. In web-direct mode each agnt session becomes exactly one sidebar “Workspace” item (kind:"cloud", current_session_id = its own id), grouped by repo name. There's no separate workspace list to reconcile — the session is the item.
AgentSession DO
agnt's Cloudflare Durable Object, one per session, named by the session id (apps/backend/src/agent-session/agent-session.ts). Owns the folded transcript (DO SQLite), the execute queue, and every connected client socket. Its first frame to any client is always session.snapshot.

1Auth & tokens

The auth story is a two-tier token design. The bearer (deus_cloud_session) is your identity for a day; the session_token is a narrow, per-session capability minted from it on demand. Nothing that can drive an agent ever ships with broad scope, and nothing broad ever touches a WebSocket URL.

Getting the bearer — the web login dance

On a Mac-closed boot, webCloudDirectConfig.ts gates the app: no bearer in sessionStorage → redirect to the deus-cloud worker's /auth/login. The worker (agnt: apps/deus-cloud/src/routes/auth.ts + auth/*) runs a standard PKCE dance against WorkOS AuthKit and delivers the minted JWT back to app.deusmachine.ai in a URL fragment:

Three token sources, one shape

The direct lane needs a session_token per session. Where it comes from depends on where you're running — cloudDirectToken.ts picks via pickCloudDirectTokenSource():

  • backend (desktop default): ask the local deus backend, which holds cloud credentials pushed at login. The existing seam; no browser-side auth at all.
  • workos-web (web-direct default): use the sessionStorage bearer to call the exchange endpoint straight from the page (exchangeSessionToken.ts).
  • workos-desktop (override-only today): the renderer asks Electron main via IPC (deus_cloud:mint_direct_token in apps/desktop/main/deus-cloud-direct-token.ts); main does the exchange with its stored bearer.

An explicit localStorage deus.cloudDirectTokenSource override wins; otherwise web mode implies workos-web, else backend. All three resolve to the same shape: {token, base_url, provider_session_id, expires_in} — the rest of the lane doesn't know or care which source produced it.

The bearer never enters the renderer.On desktop, the WorkOS-backed bearer lives only in the Electron main process (safeStorage-encrypted); the renderer receives narrow session_tokens over IPC and nothing more.

Exchange and acceptance, in one breath

The exchange (agnt: routes/dashboard/session-tokens.ts, PR #165) runs behind dashboardAuthMiddleware: verify the bearer JWT, check the client against DASHBOARD_ALLOWED_CLIENTS, check the account exists and is active. Authorization is then active org membership, re-checked at every mint. The resulting token is accepted by agnt's general authMiddleware (Bearer header, or ?token= only on WebSocket upgrades, because browsers can't set WS headers), and validateSessionAccess reduces to a pure claim comparison: sid === :id.

Keeping tokens fresh

useCloudDirect.ts owns freshness on the client: a query keyed ["cloudDirectToken", sessionId, providerSessionId] with staleTime = 0.8 × expires_in (~48 min on the default hour) and a refetchInterval anchored to dataUpdatedAt so component remounts don't reset the clock. useDeusCloudSession.ts runs a 15-minute heartbeat (desktop: triggers main-process silent refresh) and — crucially — on any auth change it resets the ["cloudDirectToken"] queries: dropping the token tears down the socket, so account B never streams on account A's token.

Desktop login end-to-end: loopback, safeStorage, rotation, and the 503 trick

apps/desktop/main/deus-cloud-auth.ts implements the only client that gets a WorkOS refresh token. Login: spin a loopback server on 127.0.0.1, open the system browser with a PKCE challenge, receive the callback locally, and call POST /auth/desktop/exchange on deus-cloud — which returns session_token (the 24 h bearer) plus refresh_token. (Browser clients asking for the desktop flow get a 501 from parseBrowserClient.)

  • Storage: deus-cloud-session.json, safeStorage-encrypted, mode 0600, atomic writes (safe-storage-file.ts).
  • Silent refresh: within 6 h of bearer expiry, single-flight, via POST /auth/desktop/refresh. WorkOS rotates refresh tokens on every use — and deus-cloud goes as far as returning the replacement refresh token inside the body of a 503 error, which the desktop persists from the error path. Losing a rotated token would strand the session, so the rotation is honored even when the request "failed".
  • Failure taxonomy (workos.ts: isInvalidRefreshToken): only invalid_grant/400 means the token is dead → full sign-out including device-key revocation. 5xx is operational → keep the session and retry later. 401 on refresh = revoked → sign out.
  • Provisioning (deus-cloud-provision.ts): after login, mint a per-device org API key (agnt_sk_live_*, labeled with the hostname, stored hashed with createdBy=accountId) via POST /dashboard/orgs/:orgId/api-keys, then push {apiKey, claudeOauthToken, deusCloudUrl, deusCloudSessionToken, orgId} to the local backend's /api/settings/cloud/credentials. That push is what makes the backend token source work.
Exchange authorization: membership, not ownership — and why that's correct

The exchange checks that you hold an active membership in the session's organization. It does not check per-session ownership — deliberately. agnt sessions record no authenticated owner: user_id is an opaque integrator-supplied value and is null for the deus flow, so an ownership check would 403 every real session. And the exchange is strictly weaker than what any org member can already do: with the org's API key, POST /sessions/tokens (routes/tokens.ts) mints the same-shaped token for any org session. Two more properties worth knowing:

  • Not-found and not-a-member both return an identical 403 — no session-id probing.
  • The body is tolerant-empty but strict-malformed; expires_in clamps to 60…86400, default 3600.
What a session_token can and cannot do

Acceptance lives in agnt: middleware/auth.ts (which also handles agnt_sk_ keys by hashed lookup, and skips /dashboard — that surface is bearer-only). A session_token:

  • Can: read GET /sessions/:id (snapshot) and upgrade GET /sessions/:id/ws — with ?token= accepted on the upgrade only.
  • Cannot: POST /sessions/:id/messages (rejected outright), list sessions, create sessions, or touch any other org resource. In the direct lane, sending is a message.send frame on the already-authorized socket — the token's only write power is the socket itself.
JWT plumbing and edge cases
  • One secret, two services. deus-cloud signs and agnt verifies with the same HS256 JWT_SECRET (hand-rolled WebCrypto in packages/auth/src/jwt.ts). A bad_signature in the wild means secret drift, not an attack — rotate-jwt-secret.sh sets both sides.
  • A session_token can outlive the bearer. Both cap at 24 h and there's no revocation list; revoking a membership takes effect at the next mint, not on live tokens.
  • CORS trivia. agnt's CORS is * — safe because auth is Bearer, never cookies. deus-cloud's CORS does not include app.deusmachine.ai: the app only ever navigates there, and redirects aren't CORS-gated. DEUS_APP_ORIGIN's only job is the return_to allowlist (auth-state.ts: resolveReturnTo — PR #166).
  • Tab-scoped bearer. sessionStorage means a new tab is a fresh login round-trip — silent if the WorkOS cookie is still alive, but a round-trip nonetheless. redirectToWebCloudLogin carries a 10 s cooldown (deus.cloudLoginAt) to break redirect loops.
  • The lapsed-bearer edge. If a bearer dies and the first failing call is the token mint (not discovery), the failure surfaces as a lane error rather than a re-login redirect. In practice discovery fires first and its 401 → handleWebCloudSessionExpired → clean re-login.

2Discovery & the data adapter

A bearer that can mint session tokens is useless if you don't know any session ids. PR #167 closed that loop with two read endpoints, and cloudDataAdapter.ts turns their answers into the exact shapes the existing UI already renders — so the sidebar, session header, and routing all work unmodified with no Mac anywhere.

The agnt side: two endpoints

  • GET /dashboard/orgs — your active memberships joined to organizations (agnt: routes/dashboard/orgs.ts).
  • GET /dashboard/orgs/:orgId/sessions — sessions inner-joined to their workspaces, newest first (routes/dashboard/sessions-list.ts, behind requireOrgAccess). Each row projects a DashboardSessionSummary (contract in @deus-hq/api, snake_case wire, canonical status enums): title from session metadata, repo from workspace config (with managed-repository ids batch-resolved to names), branch, and sandbox_id taken from the workspace row — the session row's copy is often null.

The deus side: the adapter

On a web-direct boot, main.tsx installs the adapter as the q: client's request interceptor before React mounts. From then on, every one-shot resource request the app would have sent to the Mac gets answered locally: 

installCloudDataAdapter() — the interceptor switch
  "workspaces"  → fetchAllCloudSessions() → mapToRepoGroups()   (the sidebar)
  "sessions"    → same fetch, session rows for a workspace
  "session"     → toSession(providerId)                         (the detail row)
  "settings"    → { onboarding_completed: true }                (a boot key, not data)
  "messages"    → falls through — the session socket owns the transcript
  anything else → null → caller sees "not available without a Mac backend"

The mapping is deliberately lossy-but-sufficient: each agnt session becomes one sidebar Workspace item (kind:"cloud", id = the agnt session id, current_session_id = itself, provider_session_id = its workspace's id on the session row, worktree fields nulled), grouped by repo name with "Cloud" as the fallback group. Session status maps running→working, error→error, else idle; workspace status maps provisioning→initializing, error→error, deleted→archived, else ready.

Keeping the Mac transport dark

The interceptor seam lives in query-protocol-client.ts (setQueryRequestInterceptor, exported via platform/ws). It is null on every Mac-backed build — byte-identical behavior. When set:

  • connect() opens no socket but reports connected = true and fires notifyConnectionChange(true). Subscription effects gate on isConnected(); without this the app would render its offline state forever.
  • subscribe() returns a no-op unsubscribe — no frame ever leaves.
  • sendRequest() consults the interceptor first; a null answer falls through to the dead socket and rejects.
  • sendCommand() / sendMutate() reject eagerly with “X is not available without a Mac backend” — honest, by-design absence rather than a hang.
The adapter is the connection.connect() opening no socket yet reporting connected is not a hack — “connected” means “reads will be answered”, and in web-direct mode the answerer is the adapter.

Why must the socket stay dark rather than coexist? Because useQuerySubscription writes every q:snapshot as a full setQueryData replace. Any live socket answering workspaces or session would clobber the adapter-served cache; a live messages lane would clobber the socket-driven fold. One transport per resource, ever.

Boot order (load-bearing)

main.tsx, before ReactDOM.render:
  1. captureCloudSessionFromFragment()   // fresh redirect's bearer → sessionStorage, scrub URL
  2. installCloudDataAdapter()           // reads must be answerable before anything fetches
  3. ensureWebCloudSession()             // no bearer → redirect to login (never flashes UI)

Capture-before-install so the very first adapter fetch has the bearer; install-before-ensure so a signed-in boot never flashes the login screen.

Adapter mechanics: the 3-second cache, auth guard, and hardcoded harness
  • One round-trip, many consumers. fetchAllCloudSessions() (orgs → Promise.all per-org session lists → flat array) memoizes its in-flight promise for LIST_TTL_MS = 3000; errors evict immediately. Sidebar and session panel mounting together share a single fetch.
  • Auth guard. dashboardGet resolves the base URL (resolveAgntBaseUrl, default api.deusmachine.ai) and attaches the sessionStorage bearer; a missing bearer or a 401 throws CloudSessionExpiredError, and withAuthGuard converts that into handleWebCloudSessionExpired() — clear the bearer, cooldown-guarded redirect to login.
  • toSession hardcodes agent_harness:"claude-code". The list endpoint doesn't carry harness; codex cloud sessions misreport until the socket connects. Cosmetic — the send path carries the real harness (§4).
  • has_more is surfaced by agnt (limit 101) but ignored by the adapter — more than 100 sessions per org silently truncates. Known, accepted for now.
  • Paused/stopped sandboxes map to “ready”. mapWorkspaceState flattens them deliberately: wake-on-send carries the real truth in-chat, and a “paused” sidebar would just be noise.
Cold-boot request census and the freshness gap

Everything a Mac-closed boot sends, in order:

GET  cloud.deusmachine.ai/auth/…            (only if no bearer — the login dance)
GET  api.deusmachine.ai/dashboard/orgs
GET  api.deusmachine.ai/dashboard/orgs/:id/sessions   (× orgs, shared via 3 s cache)
     — on opening a session —
POST api.deusmachine.ai/dashboard/sessions/:providerId/token
WSS  api.deusmachine.ai/sessions/:providerId/ws?v=…&token=…

Nothing else succeeds — and that's the point. Two consequences:

  • No push for the list. The workspaces query keeps its Mac-lane settings (staleTime: Infinity, no focus/interval refetch) because the WS normally provides freshness — but here there is no WS for the list. Refresh happens via mutation-side invalidations and remounts. A cloud session started elsewhere won't appear until something invalidates. Known gap (§Status).
  • Harmless Mac-only chatter. A few calls fire and reject by design: bulk diffStats rides Promise.allSettled, the cloud-connect POST is best-effort wrapped in a catch. Expected console noise, not bugs.
Why the list endpoint exists at all

PR #165 gave the bearer a per-session token exchange — but you had to already know a session id, which only a Mac-synced client would. PR #167's list is what makes a Mac-closed browser able to find its sessions. #165 = “may I open this door?”; #167 = “which doors are mine?”.

3The render lane

Open a cloud session and the direct lane assembles per session: useCloudDirect mints the token and owns the socket lifecycle; cloudSessionSocket.ts speaks the wire; cloudFrameHandler.ts adapts agnt frames into the fold; agentEventFold.ts turns them into cache rows React renders. The design premise: the DO's snapshot is authoritative and cheap to re-apply, so the client never needs sequence-number bookkeeping.

What agnt sends

GET /sessions/:id/ws → validateSessionAccess → the AgentSession Durable Object accepts the socket (Cloudflare hibernation API) and immediately sends session.snapshot. After that, live frames: the admission bracket for user messages (turn.started then message.started/part/ended), the sidecar engine's events re-broadcast verbatim (assistant messages, full-snapshot message.part upserts, typed message.part.deltas), every terminal funneled through one emitTurnEnded → turn.ended, plus session.usage / session.compaction / session.error. The same socket also carries non-render traffic (workspace.state, pty.*, fs.*, diff.*, browser.*, permission/question frames) — the direct lane currently consumes only the render frames.

The snapshot is not a log.It is the current truth — already-folded messages plus durable turn outcomes — re-sent whole on every (re)connect. Its events array is filtered to workspace lifecycle only; nothing about it is replayable history.

The unroll: snapshot → fold

makeCloudFrameHandler does one tiny, critical rewrite — the frame's sessionId from agnt's provider id to the deus session id, the key the fold uses everywhere — then hands the frame to foldEvent. Seq-free by design

The Mac lane's event stream carries per-session sequence numbers, and the frontend runs the engine's SeqCursor: skip duplicates, on reset delete the fold and refetch, on gap seek and refetch. The direct lane has none of that — agnt frames carry no seq, so gap/reset/duplicate arithmetic can't even fire. Correctness comes from a different invariant: every write is an upsert by derived id, and every reconnect re-folds a fresh snapshot. Idempotence replaces ordering. (Pinned by test/unit/session/directLaneRoundtrip.test.ts.)

The socket contract: query token, hibernation pings, backoff, and hard throws
  • URL: wss://{base}/sessions/{providerSessionId}/ws?v=API_VERSION&token=…. The token rides the query string because browser WebSockets can't set headers; agnt accepts query tokens only on upgrades. ?v= older than API_VERSION (“2026-08-14”) gets a typed 400; non-upgrade requests get 426.
  • Pings: a literal "ping" every 30 s, answered by the DO's setWebSocketAutoResponse("ping","pong") pair — the Cloudflare runtime answers without waking a hibernated DO. Liveness costs zero compute.
  • Deadlines: 10 s handshake deadline; reconnect backoff min(500·2ⁿ, 15000) with max 8 retries before onDown; ready() bounded at 30 s.
  • send() throws synchronously (“Cloud session socket is not connected”) when the socket isn't OPEN — the send lane leans on this for clean mutation rejection (§4).
  • Token re-mint ≈ every 48 min is a full reconnect, on purpose. New token → new URL → new socket → fresh snapshot re-fold. The unroll makes it visually seamless, so no in-place re-auth protocol was worth building.
Cache-write semantics: merges, COALESCE, the cancelled divider, and the one-writer rule
  • writeMessage upserts by row id into the PaginatedMessages page. An existing row keeps its previous seq and first sent_at; parts go through mergePartsById — for a shared part id the next value wins, but cache-only parts survive. Never a wholesale parts replace. (Seeding the fold from the HTTP page was considered and rejected: unlike agnt's in-channel snapshot, deus's page fetch races the WS.) If the session is live and no page exists, the fold seeds a fresh one ({messages:[row], compactions:[], has_older:false}) — the Mac-closed no-HTTP-seed case.
  • Turn accounting (writeTurnAccounting) stamps the turn's last top-level assistant row: null tokens/cost/cancelled_at leave the cached value (COALESCE expressed as conditional spread), while turn_stop_reason writes unconditionally. A cancelled turn with no assistant row appends cancelled-${turnId} — the live “Response stopped” divider, same derived id the backend would write, so replay dedupes.
  • Compactions upsert by compaction_id (status replaces, optional fields COALESCE, created_at anchored) and schedule a debounced requestRefetch — which is inert in direct mode because the messages query is enabled:false: TanStack skips the fetch, and the projection is already the delivery.
  • One writer module. commitTranscriptOrder lives inside agentEventFold.ts even though it's a plain cache write, so the messages key has exactly one writer module in the codebase. If you're writing that key from anywhere else, you're building a bug.
  • Shared row doctrine (shared/conversation-rows.ts): one row implementation, two stores. The backend binds it to SQL — messages use ON CONFLICT updates, never INSERT OR REPLACE (which would cascade-delete parts); parts do use INSERT OR REPLACE because a part owns all its columns. The frontend spreads the same semantics onto cache rows. Same derived ids (echo-${turnId}, cancelled-${turnId}) keep the stores convergent.
Contrast: how the Mac lane consumes the very same agnt socket

The deus backend's cloud driver (apps/backend/src/services/agent/cloud/) connects to the same DO but plays a different role: it mints a synthetic per-session seq for the q:event agent:event re-broadcast, and it does not backfill snapshot history — Mac SQLite already is the history; it only gap-heals a live turn's missed turn.ended from state.turns. The browser's backfillSnapshot, by contrast, is the only history source in the direct lane. Both lanes share the fold module but keep separate module-level folds maps — a desktop running flag-on Path B never cross-contaminates its Mac-lane folds.

Accepted roughness and open items in the render lane
  • session.error shape mismatch: the hook reads frame.error as a string, but agnt sends {error:{code,message}, recoverable, turnId?} — real errors surface as a generic “Session error”, and recoverable/turnId are ignored. Known, accepted for now.
  • workspace.state frames are ignored — no provisioning/wake UI in the direct lane yet (on the punch-list, §Status).
  • Restated turn.endeds drop L2 payloads (files/gitSync) — turn-diff UI after a reconnect won't see them.
  • The file-header comment in cloudFrameHandler.ts is stale — it still mentions routeEnvelope/synthetic-seq, describing the backend twin. The function docblocks and code are the seq-free truth. (Gotcha card below.)

4The send lane

Sending is where the direct lane earns its keep: type on a phone, and an agent turn starts in a cloud sandbox with no Mac involved. The design has three pillars: the caller mints the turnId (the correlation key exists before anything is sent), the wire carries no credentials ever (agnt resolves them at dispatch), and the user's message converges from three producers onto one row by derived id.

Routing the mutation

useSessionActions.sendMessage → useSendMessage.mutateAsync({ …, turnId: newTurnId() })  // uuidv7, caller-minted

onMutate (BOTH lanes):
  cancel in-flight messages queries · snapshot workspaces cache
  push optimistic bubble = the future echo  (id echoMessageId(turnId), parts createUserEchoParts — byte-for-byte, incl. multimodal)
  sidebar status → working

mutationFn, in order:
  1. getDirectSession(sessionId)?   → YES → direct.sendMessage(…)   // fire-and-forget; return
  2. isDirectSessionCached(id)?     → YES → throw SendRejectedError("The cloud connection isn't ready yet")
  3. Mac lane: sendCommand("sendMessage") → !ack.accepted → SendRejectedError
     transport failure              → HTTP fallback, same fields

Step 2 is the subtle one: the session is known to be direct, but its channel isn't registered (socket mid-connect, or the token mint failed). Falling through to the Mac/HTTP path would dispatch a real turn whose response the disarmed read-lanes could never render — a bubble stuck forever. Failing fast is the only honest outcome.

“Accepted” means the frame left an open socket.The direct lane awaits no ack — unlike the Mac lane's quick-ack. Business rejection arrives later as an error frame; transport failure throws synchronously and rolls the optimistic state back.

Inside the direct channel

useCloudDirectSession registers the live channel in directSessionRegistry. Its sendMessage first enforces one-live-turn — if the fold shows an active turn, throw “The agent is still working…” — then sends: 

{ type: "message.send",
  text, turnId,
  idempotencyKey: turnId,                  // names the DELIVERY, not the content
  options: { harness,                      // ALWAYS when known — agnt keys credential resolution on it
             model?, thinkingLevel? } }    // NEVER apiKey / authKind / codexAuthJson (pinned by test)

The guard lives in the channel because that's where the fold state is in reach — and it must live somewhere client-side, because agnt itself queues overlapping sends (MAX_QUEUED_EXECUTES = 16; “overlapping messages are the normal case for chat integrations”). The harness field matters more than it looks: agnt resolves the org credential at dispatch time by harness, so a codex turn sent bare would resolve the Claude credential and run as claude. Pinned by test.

Three producers, one echo row

agnt admission & dispatch, precisely
  • Credential boundary. postMessage rejects inline codexAuthJson outright — the durable queue must never put a refresh token at rest. (Claude's inline apiKey predates the rule; recorded follow-up.)
  • Idempotency receipts. sha256(prompt) stored under idem:${key}. Same key + same hash → replay {deduplicated:true}, no second turn. Same key + different hash → conflict. Receipt and user row are written in one synchronous DO block; the queue-capacity check runs before persist so a 429 never orphans a prompt.
  • The turnId crack. agnt accepts the client's turnId unless it was already used in the session — then it silently mints its own. The optimistic bubble keyed on the old id never reconciles and is retired only by a refetch. Deliberate: honoring a colliding id would corrupt history; a stuck bubble is the cheaper failure.
  • Dispatch (execute-queue.ts): harness verdict (defer unknown, reject unsupported) → buildDispatchedCommand: a client credential wins if present, else resolveTurnCredential(harness) — a bounded (Promise.race timeout) Postgres lookup of the org secret (CLAUDE_CODE_OAUTH_TOKEN → oauth, or CODEX_AUTH_JSON), decrypted at dispatch, injected into the sidecar's agent:execute, never persisted in DO state. On failure/timeout: dispatch credential-less and let the sidecar's ambient fallback try. This is the “phone / Mac-off” path in one sentence.
One-live-turn: who enforces it on which path
Path Enforcement
Direct lane (browser → agnt) Fold guard in the channel (useCloudDirectSession): any state.turns entry active → throw before send.
Mac → cloud Backend cloud driver's in-memory liveTurnId + commands.ts ACTIVE_TURN_STATUSES.
Mac → local Status guard + the agent-server wire's own turnActive rejection.
agnt itself None. Queues up to 16 overlapping sends and runs them in order — the guard is client courtesy, not a platform invariant.

The known hole: the guard is per-client best-effort. A client connecting mid-turn gets a snapshot whose backfill skips currentTurnId (no turn.started restated for the live turn), so its guard won't trip and agnt queues the overlap. Same class of gap as the Mac driver's in-memory liveTurnId after a backend restart. snapshot.state.currentTurnId is available and unused by the guard — an open question, not an oversight anyone defends.

Stop flow and client-side error handling
  • Stop: useStopSession → direct.cancel() sends {type:"agent.cancel"} with no turnId — the DO targets state.currentTurnId. A still-queued turn is spliced out with an immediate turn.ended{cancelled}; a dispatched turn sets pendingCancelTurnId, fires best-effort agent:cancel, and a cancel-confirmation watchdog guarantees the terminal. The fold projects the “Response stopped” divider (cancelled-${turnId}) either way.
  • onError: emitSendAttemptFailed — which escalates the Mac connection-health store — is gated on !isDirectSessionCached, because the direct socket's “Cloud session socket is not connected” matches the same substrings while being a different transport entirely. Then dropOptimisticMessage filters exactly this send's bubble by echoMessageId(turnId), and rollbackSendStatus picks its remedy: SendRejectedError → refetch; transport death → restore the workspaces snapshot.
  • Flag-off fleet: with deus.cloudDirect unset the registry is always empty, so both direct branches of the mutation are provably dead code — the flag's blast radius is zero.

5Lane gating

Both lanes ultimately write the same TanStack key — ["sessions","messages", id]. The entire gating design exists to enforce one sentence:

Exactly one lane may drive the messages cache key for a given session at any moment.

The oracle: useIsDirectSession

One predicate decides everything: isDirectRow = workspace_kind === "cloud" && !!provider_session_id, computed with a select: over the same sessions.detail cache entry that useSession keeps WS-fresh — an added observer, not a second fetch. (sessionDetailQueryOptions(id) is the one shared query definition, spread by useSession, useWorkingSessionIds, this hook, and the hover prefetch.) The result is tri-state, and the third state is the point: 

useIsDirectSession(sessionId) — over the sessions.detail row
  row not loaded yet                    → undefined  → arm NEITHER lane
  workspace_kind ≠ "cloud" (worktree),
    or flag off                         → false      → Mac lane owns the session
  cloud, provider_session_id null       → false      → Mac lane (a brand-new cloud tab renders
                                                       via the Mac lane until the first send
                                                       assigns provider_session_id — then flips)
  cloud + provider_session_id set       → true       → direct lane owns the session

Strict arming — === false, never falsy

  • useMessages arms its HTTP queryFn, the WS messages subscription, and the reconnect-invalidate only when direct === false.
  • SessionPanel arms useAgentEvents(direct === false ? id : null) and useCloudDirect(id, direct === true, provider_session_id).

undefined arms neither, and the strictness is justified by asymmetric failure modes: a wrongly-armed Mac lane clobbers a fold irrecoverably (an authoritative-empty HTTP fetch overwrites the folded transcript, and under staleTime: Infinity nothing ever heals it), while a wrongly-held lane merely delays a fetch by one round-trip. When in doubt, hold.

Below hook-space

Mutations and prefetchers can't call hooks, so isDirectSessionCached(id) runs the same predicate over queryClient.getQueryData — with uncached = not-direct. It powers the send lane's fail-fast and error gating (§4), and prefetchWorkspace uses it to skip the messages warmup for direct sessions: the hover prefetch is a fetchQuery with staleTime: 0, i.e. a forced overwrite — pointed at a folded transcript it would be the exact clobber the arming rules exist to prevent.

The second, sharper signal is the registry (directSessionRegistry.ts): presence in the map means “this session is served by a live direct channel right now” — not “this session is direct in principle”. Its disposer compares-before-delete because React 18 can run a fast remount's new effect before the old cleanup, and blind deletion would deregister the new channel.

The oracle's plumbing: where workspace_kind actually comes from

The backend's SESSION_DETAILS_SELECT joins workspaces twice: owner_ws on s.workspace_id — always present, and the source of workspace_kind — versus current_ws on current_session_id, which contributes slug/state only for the active session. So workspace_kind is a property of the session's owning workspace, stable across the session's life; in web-direct mode the adapter synthesizes the same shape client-side (toSession). Either way the oracle reads one cache row and nothing else — the gating decision is O(1) and always as fresh as the sessions.detail entry.

Why the tri-state flip on first send is safe

A brand-new cloud session has no provider session yet: it renders via the Mac lane (backend-served history, empty), and the first send — routed through the Mac lane, step 3 of the mutation — causes the backend to provision the agnt session and write provider_session_id onto the row. The sessions.detail subscription delivers the update, isDirectRow flips to true, the Mac read lanes disarm, and useCloudDirect arms and connects. The handoff is glitch-free because both lanes write upsert-style into the same key with the same derived ids — the fold simply takes over rows the Mac lane seeded.

Gotchas

Arm on === false, never on falsy

useIsDirectSession returns undefined while the row loads, and undefined must arm neither lane. A truthiness check would arm the Mac lane during load — and a wrongly-armed Mac lane overwrites the folded transcript with an authoritative-empty fetch that staleTime: Infinity then preserves forever.

The snapshot is not a log

session.snapshot.events is filtered to workspace lifecycle only. History is messages[] (already folded) plus state.turns (durable outcomes, ≤100). Never write code that expects to replay events from a snapshot.

The settings stub is a boot key, not data

The adapter answers settings with {onboarding_completed:true} because the app shell gates mounting on that query resolving. Don't extend it into a settings implementation — it exists to open a gate, nothing more.

Parts merge by id — never wholesale

mergePartsById: for a shared part id the next value wins, but cache-only parts survive. A wholesale parts: replace would drop optimistic and mid-flight parts and is always wrong in this codebase. (Mirrored in SQL: parts may INSERT OR REPLACE; messages must not.)

The mid-turn-joiner guard hole

A client connecting mid-turn sees no turn.started for the live turn (backfill skips currentTurnId), so its one-live-turn guard won't trip — and agnt happily queues the overlap. snapshot.state.currentTurnId is available and unused by the guard; open question.

sessionStorage bearer is tab-scoped

Every new tab is a fresh login round-trip (silent if the WorkOS cookie is alive). Don't “fix” it by moving to localStorage without deciding the multi-account and logout story first — tab-scoping is currently doing quiet isolation work.

A session_token can outlive the bearer

No revocation list exists. Revoking a membership bites at the next mint, not on tokens already in flight (≤24 h worst case). Design reviews of new endpoints should assume this.

Web-direct list freshness is invalidation-only

No WS pushes the session list in web-direct mode; the workspaces query is staleTime: Infinity with no focus/interval refetch. A session started elsewhere won't appear until a mutation invalidates or the app remounts. Known gap, on the punch-list.

The stale header comment in cloudFrameHandler.ts

The file-top comment still describes routeEnvelope/synthetic-seq — that's the backend twin's world. The function docblocks and the code are the seq-free truth. Trust them, and fix the header when you touch the file.

agnt queues; deus enforces

One-live-turn is client-side courtesy, per path (see the table in §4). agnt itself queues up to 16 overlapping sends and runs them in order. If you see a double-run, suspect a guard that didn't trip — not platform breakage.

Discovery hardcodes claude-code

toSession stamps every discovered session agent_harness:"claude-code" — the list endpoint doesn't carry harness. Codex cloud sessions misreport until the socket connects; the send frame's options.harness carries the truth where it matters (credential resolution).
