**Project and workspace UI composition: bounded plan**

Read-only exploration, 14 September 2026. Latest user constraint: Project PRs open externally on GitHub/in a new browser tab. There is no requested internal PR-detail viewer. This plan supersedes any earlier suggestion of adding one.

1. **Keep the application shell, separate the selected page.** `MainLayout` owns global workspace selection at [line 96](../../../apps/web/src/app/layouts/MainLayout.tsx:96), resolves it from repository groups at [line 123](../../../apps/web/src/app/layouts/MainLayout.tsx:123), connects its cloud channel at [line 137](../../../apps/web/src/app/layouts/MainLayout.tsx:137), polls its PR at [line 178](../../../apps/web/src/app/layouts/MainLayout.tsx:178), and switches settings/automations/content at [line 508](../../../apps/web/src/app/layouts/MainLayout.tsx:508). Retain app-lifetime auth, sidebar, global dialogs and notification infrastructure. Introduce a focused Project page alongside a workspace page; move selected-workspace-only queries/effects into the workspace controller. Use one explicit page target rather than adding `projectOpen` to a growing set of independent visibility booleans. This is a bounded composition change, not a requirement to rewrite every route.

2. **Two entity shells should share their useful parts.** Make `ProjectPage` under `features/projects/ui` own ProjectHeader, coordinator conversation and Notes/Agents/PRs/Context. Extract/retain a `WorkspacePage` from the workspace branch of [MainContent.tsx:354](../../../apps/web/src/app/layouts/MainContent.tsx:354), with WorkspaceHeader, conversation tabs and execution tools. `WorkspaceHeader` currently requires repository identity and accepts branch, setup tasks, cloud wake and workflow status ([line 43](../../../apps/web/src/features/workspace/ui/WorkspaceHeader.tsx:43)); those should not become a bag of undefined props on a Project header. Share a small header frame or existing primitives only if both shells actually repeat the same rendering. Do not add `isProject` to MainContent/WorkspaceHeader/ContentView.

3. **Share conversation rendering; retain distinct submission controllers.** `SessionPanel` already takes explicit session/workspace props ([line 33](../../../apps/web/src/features/session/ui/SessionPanel.tsx:33)); it does not read global selectedWorkspace. Its transcript fold, pagination, question overlays and `Chat` are strong reusable components. `ChatArea`, however, is specifically a workspace tab controller: [line 54](../../../apps/web/src/app/layouts/ChatArea.tsx:54) calls `useChatTabs(workspace.id)`. Render the coordinator conversation directly, rather than fabricating a workspace tab collection for Project home. Clean the actual couplings: SessionPanel's Git RPC map currently invents `main` defaults ([line 95](../../../apps/web/src/features/session/ui/SessionPanel.tsx:95)); its login action directly selects the workspace Terminal tab ([line 301](../../../apps/web/src/features/session/ui/SessionPanel.tsx:301)). Supply optional scope/action callbacks instead of pretending the Project has Git/runtime tools.

   The significant behavioral seam is sending: [SessionComposer.tsx:22](../../../apps/web/src/features/session/ui/SessionComposer.tsx:22) owns `useSessionActions`, which directly dispatches a session turn. Project chat inputs must enter the Project's durable input/orchestration path. Share `MessageInput`, per-session draft/model state and transcript UI, with narrow ProjectCoordinatorConversation and WorkspaceConversation controllers supplying submit/stop semantics. Reusing the direct sender unchanged would bypass the newly designed inbox. Do not create a second message renderer merely to alter sending.

4. **Share controlled panel chrome, not workspace tab registration.** The existing [ContentTabBar.tsx:107](../../../apps/web/src/app/layouts/ContentTabBar.tsx:107) fetches settings, local/cloud simulator state and mobile-project detection. Its tab registry is the workspace's execution tools. Extract only a small controlled tab-strip view—items, active key, selection and optional indicators—if useful. Keep `ProjectPanel` keys (`notes`, `agents`, `prs`, `context`) separate from `ContentTab`. The shared pieces are visual tab buttons, scroll/overflow handling, resizable-panel primitives and shortcuts; [usePanelShortcuts.ts:14](../../../apps/web/src/app/layouts/hooks/usePanelShortcuts.ts:14) is already props-driven. A general panel/plugin registry is unnecessary.

5. **Project Context gets its own data scope while reusing file rendering.** [FileTree.tsx:20](../../../apps/web/src/features/file-browser/ui/components/FileTree.tsx:20) already accepts nodes, selected path and callbacks; it can display the Project namespace. [MarkdownRenderer.tsx:45](../../../apps/web/src/components/markdown/MarkdownRenderer.tsx:45) accepts Markdown plus file/external-link handlers and can render Project notes. In contrast, [FileBrowserPanel.tsx:214](../../../apps/web/src/features/file-browser/ui/FileBrowserPanel.tsx:214) fetches by workspace ID and includes Git filters; [FileViewer.tsx:59](../../../apps/web/src/features/file-browser/ui/FileViewer.tsx:59) fetches a working-tree file. Reuse their display portions where worthwhile, with a separate Project document container owning revisioned reads/saves/conflicts. Do not point a fake workspace ID at a Project folder or treat a draft file as a published Project revision.

6. **Separate screen size from execution capabilities.** Desktop and browser should mount the same ProjectPage and feature panels. At narrow widths show one selected panel; at wide widths use the chat/content split. Reuse the same coordinator conversation and feature panels in both arrangements. Existing [MobileLayout.tsx:82](../../../apps/web/src/app/layouts/MobileLayout.tsx:82) is a workspace controller with chat/code/device semantics, so avoid expanding it with every Project combination. A small Project responsive arrangement is clearer. Feature availability comes from the selected scope and service capabilities, while [platform/capabilities.ts:25](../../../apps/web/src/platform/capabilities.ts:25) continues to own genuinely native capabilities. Do not copy the blanket direct-web hide from [content-tabs.ts:64](../../../apps/web/src/app/layouts/content-tabs.ts:64) into Project panels: durable Notes/Agents/PRs/Context can be cloud-service reads while runtime tools remain unavailable/asleep. Keep transport decisions in data/action adapters, not repeated `isCloud`/`isElectron` branches inside cards.

7. **PR rows remain external links.** Project PRs needs a collection, counts and status indicators, not another editor tab type. Existing [PRActions.tsx:180](../../../apps/web/src/features/workspace/ui/PRActions.tsx:180) shows an external anchor; [platform/native/window.ts:19](../../../apps/web/src/platform/native/window.ts:19) already centralizes Electron external-browser opening and web `window.open`. Use that established platform boundary/accessible link behavior. Keep a separate “Open agent” affordance where useful. The Project list consumes Project-associated SCM records; its generic PR status display can reuse existing status derivation without adopting workspace-specific Create PR/merge/archive control wiring.

8. **A Project agent opens the reusable workspace page with navigation context.** Use the existing exact-session opening precedent in [AutomationDetail.tsx:82](../../../apps/web/src/features/automations/ui/AutomationDetail.tsx:82): resolve/adopt provider execution, activate the target session, then open its workspace. Pass Project breadcrumb/return context as navigation chrome. Retain workspace layout keyed by actual workspace identity and Project panel state keyed by Project identity; do not create a duplicate workspace layout for each entry path. A background Project coordinator can continue through its service without keeping its React panel mounted. Avoid two mounted interactive composers owning the same coordinator session merely to preserve tab state. This approach shares the complete workspace detail while preserving a clean Project overview and browser history.

The implementation sequence can therefore be small: establish page/navigation target; isolate workspace-only controller effects; expose the narrow conversation submit/scope seam; build Project panels using existing rendering primitives; add Project reads/actions and capability-aware responsive composition. It does not require a generic UI framework, renaming all existing components or combining Project and workspace into one polymorphic mega-component.
