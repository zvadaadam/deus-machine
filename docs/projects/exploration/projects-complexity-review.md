## Additions — was each new thing necessary?

1. **Remove dormant lifecycle vocabulary before it suggests guarantees the code does not implement.** `shared/schema.ts:323` adds `pause_revision`, but its only production uses are increments in `projects/service.ts:260` and `:266`; no reader compares or exposes it. `project_dispatches.phase` admits `revoked` (`shared/schema.ts:392`, `projects/store.ts:52`) without a writer, and assignments admit `cancelled` (`shared/schema.ts:360`) without a transition. These are small but real additions to the state model readers must understand. → Cut the unused counter/increments and unused variants, or introduce them with the future behavior that actually needs them. Current Pause/Stop uses timestamps and retains prepared dispatches; this does **not** justify deleting uncertainty, closed-at checks, or source identities. Usage searches across production, tests, and documentation verified the dormant cases.

**The substantial additions are otherwise justified.** `project_inputs` must exist before an engine-echoed message; `project_dispatches` must exist before an observed `turns` row and must retain unknown admission; `project_operations` owns replayable controls/tool receipts and asynchronous preparation, not model execution. Assignments and reports preserve accepted historical evidence after later instructions. Immutable shared revisions are different from per-worktree Git checkpoints. The two PR tables distinguish a mutable GitHub association from immutable report/workspace provenance. Collapsing those records into sessions/messages or replacing them with an external workflow framework would hide the actual invariants. The small byte-storage module, ordinary backend scheduler, existing preparation pipeline, existing wire and existing chat renderer are proportionate choices.

## Premises — could an assumption be dropped?

2. **The existing navigation store treats mutually exclusive full-page views as independent booleans.** Settings, Automations and now Projects require repeated inverse writes in `apps/web/src/shared/stores/uiStore.ts:143–196`; `MainLayout.tsx:209` closes both feature pages when revealing a workspace, and `:545` selects the view through another precedence chain. The new feature extends a pre-existing premise rather than creating a distinct navigation owner. → In a separate navigation cleanup, use one active full-page view value (with its selected Project/Automation ID) and derive these booleans if old callers still need them. This would delete the repeated sibling resets and their invalid combinations; it does not require a routing framework. **Verification:** current setters explicitly close sibling views, and MainLayout renders only one, so the exclusivity assumption is evidenced in the code. Preserve selected-workspace state and modal behavior when changing it. The new core's single backend owner, separate execution process, and real asynchronous recovery do not offer a similarly safe premise to drop.

## Spread — is the concept localized?

3. **Project command and tool argument contracts have several manual owners.** Frontend actions/routes live in `apps/web/src/features/projects/api/projects.queries.ts:58–83`, REST parsing in `apps/backend/src/routes/projects.ts:21–115`, application action names plus an optional argument bag in `projects/service.ts:217–230`, and tool argument definitions/validation in both `apps/agent-server/agents/deus-tools/projects.ts:51–111` and `projects/service.ts:373–589`. The naming translation (`resume-agent`/`resume_agent`, `cancel-input`/`cancel_input`) and optional argument bag make each added action a checklist across layers. Limits have already diverged: the tool advertises at most 20 report files/PR links, while backend validation permits 24. This is not an exploitable boundary failure; it is repeated policy ownership. → Keep authorization at the backend and validation at each untrusted boundary, but share a small discriminated action/tool argument contract and named limits in `shared/projects.ts` or a neighboring schema file. Derive/infer the DTO types from it. Do **not** introduce a generic workflow registry or make the renderer know backend scheduling details merely to reduce file count.

**Necessary spread is not a finding.** The membership guard at workspace/session/automation mutations prevents those existing entrypoints from bypassing Project ownership; a single shared `assertUnmanagedWorkspace` already owns that decision. The extra native/main-process business-logic layer one might expect is absent. `SessionPanel` and the existing transcript renderer remain reused; the distinct Project composer is warranted by durable queued input and its restricted controls. Feature-local pages, dialogs, queue and PR components are normal UI decomposition, not an invented component framework.

## Duplicates — does something like this already exist?

4. **Two methods commit the same content-revision invariant.** `ProjectStore.publish()` at `apps/backend/src/services/projects/store.ts:617–629` and `report()` at `:661–673` independently merge blobs into a manifest, enforce the 256-file bound, insert a revision and advance the content head. The prototype-key correction during this review had to be applied to both merge sites, illustrating the maintenance cost. → A small private `appendRevision(project, blobs)` method in the existing store could own those steps and remove roughly a dozen duplicate lines. Keep expected-revision conflict checks, receipts and report creation in their current caller transactions. `ProjectContent` at `content.ts` owns bytes and should not acquire SQL responsibilities. No existing repository primitive was found that could replace the whole revision store; the opportunity is this one local invariant, not a new persistence abstraction.

## Verdict

**Broader simplification opportunity here — worth a separate task.** The feature is large because it delivers durable multi-agent coordination plus complete UI and tests, not because it introduces an oversized framework. The dormant states and repeated revision commit are sensible local trims; the navigation and shared-contract cleanup deserve deliberate follow-up. I would not block the verified behavior on a wider architectural rewrite or remove the persistence/recovery safeguards to make the diff look smaller.
